# ❓ FAQ — คำถามที่พบบ่อยเกี่ยวกับระบบยืมคืนหนังสือ

> เอกสารนี้รวบรวมคำถามที่ผู้ซื้อถามบ่อยที่สุด พร้อมคำตอบที่ชัดเจน
> อ่านจบแล้วจะเข้าใจว่า "ได้อะไร", "ทำอะไรได้", และ "ควรคาดหวังอะไร"

---

## 📦 1. คำถามเกี่ยวกับสินค้า

### Q: Template นี้คืออะไร?

**A:** เป็น **ระบบยืมคืนหนังสือบนเว็บ** ที่เขียนด้วย PHP + MySQL พร้อมใช้งานทันที ฟีเจอร์หลักประกอบด้วย:

- จัดการหนังสือ (เพิ่ม แก้ไข ลบ นำเข้าจาก CSV)
- จัดการผู้ใช้ (สมัคร แก้ไข เปลี่ยน role พิมพ์บัตรสมาชิก นำเข้าจาก CSV)
- ยืม-คืนหนังสือ พร้อมคำนวณค่าปรับอัตโนมัติ
- จองหนังสือออนไลน์
- Dashboard สถิติ + รายงาน + Export CSV + พิมพ์รายงาน (บันทึกเป็น PDF ผ่านกล่องพิมพ์ของเบราว์เซอร์)
- ระบบ Login แยก 3 บทบาท (Admin / Staff / Member)
- ตั้งกฎการยืม-คืนเองได้ **ในหน้าเว็บ** — วันยืม ค่าปรับ โควตา ต่ออายุ วันหยุดห้องสมุด
- ใส่เลขเรียกหนังสือ พิมพ์ฉลากบาร์โค้ด พิมพ์บัตรสมาชิก
- ใบรายชื่อโทรตามก่อนครบกำหนด + **จดได้ว่าโทรใครไปแล้ว ผลเป็นยังไง** (ระบบ**ไม่ส่งอีเมลแจ้งเตือน** — ดูข้อจำกัดท้ายไฟล์)
- กระดิ่งแจ้งเตือนในหน้าเว็บ — เจ้าหน้าที่เห็นของที่ต้องจัดการวันนี้ สมาชิกเห็นของตัวเอง
- ส่งลิงก์ตั้งรหัสผ่านใหม่ทางอีเมลได้ (ต้องตั้งค่า SMTP เอง · **ปิดไว้เป็นค่าเริ่มต้น**)
- ติดตั้งง่ายด้วย XAMPP กดปุ่มเดียว

---

### Q: เหมาะกับใคร?

**A:** เหมาะกับ:

- **นักศึกษา** ที่ต้องส่งโปรเจคจบหรือรายงาน
- **ผู้เริ่มต้น** ที่อยากเรียนรู้ PHP Backend แบบมีโครงสร้าง
- **ผู้สอน** ที่ต้องการตัวอย่างระบบจริงสำหรับสอนนักเรียน
- **Freelancer** ที่อยากมี template ไว้ต่อยอดให้ลูกค้า
- **ห้องสมุดหรือร้านขนาดเล็ก** ที่ต้องการระบบยืมคืนบนเว็บ

---

### Q: ไม่เหมาะกับใคร?

**A:** ไม่เหมาะกับ:

- องค์กรขนาดใหญ่ที่ต้องการผู้ใช้พร้อมกันหลายร้อยคน
- ระบบที่ต้องการ uptime 99.99% หรือ SLA ระดับ enterprise
- คนที่ต้องการระบบสำเร็จรูปพร้อม deploy ขึ้น cloud ทันที โดยไม่ต้องปรับแต่ง
- คนที่ต้องการให้ผู้ขายเขียนฟีเจอร์เพิ่มให้ฟรีหลังซื้อ

---

### Q: ใช้เรียนได้ไหม?

**A:** ได้เลยครับ — นี่คือจุดเด่นหลักของ template นี้ เหมาะมากสำหรับเรียนรู้:

- **Layered Architecture** — Controller → Service → Repository → Database
- **Security** — CSRF, XSS prevention, SQL Injection, Rate Limiting, Password Hashing
- **Transaction & Locking** — ป้องกัน race condition ในระบบยืม-คืน-จอง
- **CRUD + Validation** — หนังสือ, ผู้ใช้ (member+staff), หมวดหมู่

โค้ดมี comment ภาษาไทยอธิบายทุกจุดสำคัญ + มีเอกสารประกอบหลายไฟล์

---

### Q: ใช้ส่งงานอาจารย์ได้ไหม?

**A:** ได้ครับ หลายคนซื้อไปส่ง project แล้ว ระบบทำงานได้จริง มีฟีเจอร์ครบ

💡 **แนะนำ:** ซื้อแล้วควรอ่านทำความเข้าใจ flow ก่อน เผื่ออาจารย์ถามว่า "ส่วนนี้ทำงานยังไง?" จะได้ตอบได้ ในโค้ดมี comment ภาษาไทย + มีเอกสาร `FLOW.md` อธิบาย flow ทุกขั้นตอน

---

## 🧠 2. คำถามสำหรับมือใหม่

### Q: ไม่มีพื้นฐานเขียนโค้ดเลย ใช้ได้ไหม?

**A:** ขึ้นอยู่กับเป้าหมายครับ:

| เป้าหมาย | ต้องมีพื้นฐานไหม? |
|---------|----------------|
| **แค่ติดตั้งและใช้งาน** | ไม่ต้อง — มีคู่มือทุกขั้นตอน กดตามได้เลย |
| **ตั้งกฎการยืม** (ค่าปรับ, วันยืม, โควตา) | ไม่ต้อง — ตั้งในหน้าเว็บได้เลย ไม่ต้องแตะไฟล์ |
| **แก้ชื่อเว็บ / URL** | ไม่ต้อง — แก้ในไฟล์ `.env` ด้วย Notepad |
| **แก้โค้ดหรือเพิ่มฟีเจอร์** | ควรมีพื้นฐาน PHP + MySQL บ้าง |
| **อ่านโค้ดเพื่อเรียนรู้** | ไม่ต้องเก่ง — โค้ดมี comment ภาษาไทย อ่านไปเรียนรู้ไปได้ |

---

### Q: ต้องอ่านไฟล์ไหนก่อน?

**A:** แนะนำอ่านตามลำดับนี้:

1. **`README.md`** — ภาพรวมทั้งหมด + วิธีติดตั้ง + คำอธิบายระบบ
2. **`FLOW.md`** — ภาพรวมการทำงาน (ระบบทำงานยังไง ใครเรียกใคร)
3. **`ARCHITECTURE.md`** — โครงสร้างระบบ (ทำไมถึงออกแบบแบบนี้)
4. **`FAQ.md`** (ไฟล์นี้) — คำถามที่พบบ่อย

ถ้าอยากอ่านโค้ดจริง แนะนำเริ่มจาก `login.php` → `app/Services/AuthService.php` จะเห็นภาพการไหลของข้อมูลชัดที่สุด

---

### Q: โค้ดเยอะไหม? จะงงไหม?

**A:** ระบบมีไฟล์พอสมควร แต่ **จัดโครงสร้างชัดเจน** ไม่ได้กองรวมกัน:

| โฟลเดอร์ | มีอะไร | จำนวน |
|---------|--------|-------|
| `app/Services/` | กฎธุรกิจ (สมอง) | 8 ไฟล์ |
| `app/Repositories/` | SQL (คลังข้อมูล) | 9 ไฟล์ |
| root (`*.php`) | หน้าเว็บ public | ~10 ไฟล์ |
| `admin/` | หน้า admin/staff | ~19 ไฟล์ |
| `api/` | JSON API | 5 ไฟล์ |
| `includes/` | config + helper | ~8 ไฟล์ |

💡 ไม่ต้องอ่านทุกไฟล์ — เริ่มจากที่สนใจ แล้วค่อยขยายไปทีละส่วน เอกสาร `FLOW.md` จะบอกว่า "ถ้าอยากเข้าใจเรื่องนี้ ให้ดูไฟล์ไหน"

## 🧩 3. คำถามเกี่ยวกับโครงสร้างโค้ด

### Q: ใช้ MVC ไหม?

**A:** ใช้แนวคิดที่ได้แรงบันดาลใจจาก MVC แต่ **เขียนเอง (vanilla PHP)** ไม่ใช้ framework สำเร็จรูป

โครงสร้างแบ่งเป็น 4 ชั้น:

```
📋 Controller  (*.php ที่ root/, admin/, api/)  → รับ request, ตรวจสิทธิ์
🧠 Service     (app/Services/)                  → กฎธุรกิจ, ตัดสินใจ
🗄️ Repository  (app/Repositories/)              → เขียน SQL, ดึง/บันทึกข้อมูล
💾 Database    (MySQL)                           → เก็บข้อมูลถาวร
```

**ข้อดีของการเขียนเอง:** เห็นกลไกทุกอย่างชัดเจน ไม่มี framework ซ่อน เหมาะกับการเรียนรู้

---

### Q: Controller / Service / Repository ต่างกันยังไง?

**A:** เปรียบเทียบกับร้านอาหาร:

| ชั้น | เปรียบเทียบ | หน้าที่ | ตัวอย่าง |
|-----|-----------|--------|---------|
| **Controller** | พนักงานรับออเดอร์ | รับ request จากผู้ใช้ ตรวจสิทธิ์ ส่งต่อ | `login.php`, `admin/borrows.php` |
| **Service** | พ่อครัว (สมอง) | ตัดสินใจตามกฎ ใช้ transaction | `BorrowService.php` |
| **Repository** | พนักงานคลัง | ดึง/บันทึกข้อมูล เขียน SQL | `BookRepository.php` |

- **Controller** ไม่คิด ไม่ตัดสินใจ → แค่ "รับ → ส่งต่อ → แสดงผล"
- **Service** คิดและตัดสินใจทุกอย่าง → กฎทั้งหมดอยู่ที่นี่
- **Repository** แค่ดึง/บันทึกข้อมูล → ไม่มีกฎธุรกิจ

---

### Q: ทำไมโค้ดดูแยกหลายไฟล์?

**A:** เพราะออกแบบตามหลัก **Separation of Concerns** — "แยกหน้าที่ให้ชัด แก้ง่าย พังยาก"

- อยากเปลี่ยนกฎ "ยืมได้กี่เล่ม" → ตั้งในหน้าเว็บได้เลย ไม่ต้องแตะโค้ด
- อยากเปลี่ยนหน้าตาเว็บ → แก้แค่ Controller
- อยากเปลี่ยนวิธีเก็บข้อมูล → แก้แค่ Repository

ไม่ต้องไปยุ่งกับส่วนอื่น → แก้จุดเดียวไม่พังทั้งระบบ

รายละเอียดเพิ่มเติมดูได้ใน `ARCHITECTURE.md`

## 🔐 4. คำถามด้านความปลอดภัย

### Q: ป้องกัน SQL Injection ไหม?

**A:** ป้องกันครับ ทุก query ใช้ **Prepared Statements** (native, ไม่ใช่ emulated)

- ทุก SQL ใช้ `?` placeholder → ไม่มีการต่อ string ลงใน SQL โดยตรง
- ตั้งค่า `EMULATE_PREPARES = false` → ใช้ native prepared statements ของ MySQL จริงๆ
- SQL ทั้งหมดอยู่ใน Repository เท่านั้น → ดูแลจุดเดียว มั่นใจได้

---

### Q: เก็บรหัสผ่านยังไง?

**A:** เก็บแบบเข้ารหัสด้วย **bcrypt** (มาตรฐานอุตสาหกรรม)

- ใช้ `password_hash()` สร้าง hash ก่อนบันทึกลง database
- ใช้ `password_verify()` เทียบตอน login
- ไม่มีจุดไหนในระบบที่เก็บรหัสผ่านแบบ plaintext
- ถ้ามีคนแอบเข้า database ก็อ่านรหัสผ่านจริงไม่ได้

💡 ถ้าเห็นรหัสผ่านเป็นตัวอักษรยาวๆ แปลกๆ ใน database → ถูกต้องแล้ว ไม่ใช่ bug นั่นคือ hash ที่เข้ารหัสไว้

---

### Q: เอาไปใช้จริงปลอดภัยไหม?

**A:** ระบบมีมาตรการความปลอดภัยหลายชั้น:

| มาตรการ | ป้องกันอะไร |
|---------|-----------|
| **Prepared Statements** | SQL Injection |
| **`e()` ครอบทุก output** | XSS (Cross-Site Scripting) |
| **CSRF Token ทุก form** | CSRF (หลอกส่ง form) |
| **Rate Limiting** | Brute force login (เดารหัสผ่าน) |
| **bcrypt password** | รหัสผ่านรั่วไหล |
| **Session security** | Session hijacking/fixation |
| **Row Locking** | Race condition (กดพร้อมกัน) |

**แต่ต้องเข้าใจว่า:** template นี้ออกแบบเพื่อเรียนรู้และใช้งานขนาดเล็ก ถ้าจะใช้ production จริงจัง ควรเพิ่ม HTTPS, backup, logging ตามที่แนะนำในเอกสาร `FLOW.md` หัวข้อ 7

---

## 🚀 5. การนำไปใช้งานจริง

### Q: เอาไปใช้กับร้านจริงได้ไหม?

**A:** ได้ครับ ถ้าเป็นห้องสมุดหรือร้านขนาดเล็ก (สมาชิกไม่กี่ร้อยคน ผู้ใช้พร้อมกันไม่เกิน 10-30 คน) ใช้ได้สบาย

💡 **แนะนำทำเพิ่มก่อนใช้จริง:**
1. เปลี่ยน `APP_DEBUG=false` ในไฟล์ `.env`
2. ลบไฟล์ `install.php` ออก (ป้องกันคนรันติดตั้งซ้ำ)
3. เปลี่ยนรหัสผ่าน admin เป็นรหัสที่แข็งแรง
4. ตั้ง backup ฐานข้อมูลเป็นระยะ
5. ใช้ HTTPS ถ้าเปิดให้คนภายนอกเข้าใช้

---

### Q: ต้องแก้ไขอะไรเพิ่มถ้าจะใช้ production?

**A:** ระบบทำงานได้จริงตั้งแต่ติดตั้ง แต่ถ้าจะใช้ production จริงจัง ควรพิจารณาเพิ่ม:

| เรื่อง | ปัจจุบัน | ควรเพิ่ม |
|--------|--------|---------|
| **HTTPS** | รองรับแต่ยังไม่บังคับ | ตั้ง SSL certificate |
| **Email** | **ส่งได้เฉพาะลิงก์ตั้งรหัสผ่านใหม่** และ **ปิดไว้เป็นค่าเริ่มต้น** — ตั้ง SMTP เองได้ที่หน้าตั้งค่าระบบ พร้อมปุ่มทดสอบส่ง · 🔴 **ไม่ส่งอีเมลแจ้งเตือนใกล้ครบกำหนด/เกินกำหนด และตั้งใจไม่ทำ** (เมลจากเครื่องที่ไม่มีโดเมนจะลงถังสแปม เตือนแล้วไม่ถึงมือใครแย่กว่าไม่เตือน) · ทดแทนด้วยใบรายชื่อโทรตาม + กระดิ่งในหน้าเว็บ | ถ้าไม่ตั้ง SMTP ผู้ดูแลตั้งรหัสให้ที่เคาน์เตอร์ได้เหมือนเดิม |
| **Backup** | ไม่มี auto backup | ตั้ง backup ฐานข้อมูลเป็นระยะ |
| **Session** | เก็บในไฟล์ (default PHP) | เปลี่ยนเป็น Redis ถ้า traffic สูง |
| **Logging** | ใช้ error_log เขียนลงไฟล์ | ต่อ centralized logging ถ้าต้องการ |

รายละเอียดครบถ้วนอยู่ใน `FLOW.md` หัวข้อ 7 (ขอบเขตการใช้งาน) และ `ARCHITECTURE.md` หัวข้อ 6

---

### Q: รองรับผู้ใช้เยอะไหม?

**A:** ตอบตรงๆ ครับ:

- **"สมาชิก 500 คน" ที่ไม่ได้เข้าพร้อมกัน** (เข้าทีละ 5-10 คน) → ใช้ได้สบาย
- **ผู้ใช้พร้อมกัน 10-30 คน** → ทำงานได้ดี
- **ผู้ใช้พร้อมกัน 100+ คน** → หนักเกินไปสำหรับ template นี้

ระบบนี้ออกแบบมาสำหรับ "ห้องสมุดขนาดเล็ก" ไม่ใช่ "ห้องสมุดมหาวิทยาลัยที่มีนักศึกษาหมื่นคน" ถ้าต้องการ high traffic จริงๆ ต้องใช้ระบบที่ออกแบบมาสำหรับ scale นั้นโดยเฉพาะ

---

## 🛠️ 6. การแก้ไขและต่อยอด

### Q: แก้โค้ดได้ไหม?

**A:** ได้เลยครับ ซอร์สโค้ดเปิดเต็ม ไม่มีซ่อน ไม่มีเข้ารหัส แก้ไขได้ทุกไฟล์

💡 **แนะนำ:** ก่อนแก้อะไร สำรองไฟล์เดิมไว้ก่อนเสมอ (ใช้ Git หรือ copy เก็บไว้) ถ้าแก้แล้วพังจะได้ย้อนกลับได้

---

### Q: เพิ่มฟีเจอร์เองได้ไหม?

**A:** ได้ครับ โครงสร้างออกแบบมาให้ต่อยอดง่าย ทำตามแนวทางนี้:

- **ข้อมูลใหม่** → เพิ่ม Repository (SQL)
- **กฎธุรกิจใหม่** → เพิ่ม Service
- **หน้าเว็บใหม่** → เพิ่ม Controller (.php ที่ root/admin/api)
- **ค่าตั้งค่าใหม่** → เพิ่มใน `.env` + `config.php`

ตัวอย่างเช่น อยากเพิ่มช่อง LINE ID ให้สมาชิก ต้องแก้:
1. ฐานข้อมูล → เพิ่ม column ใน table `users`
2. ฟอร์ม → เพิ่ม input ใน `register.php`, `profile.php`, `admin/member_form.php`
3. Validation → เพิ่มเงื่อนไขใน `includes/functions.php`
4. บันทึก → เพิ่ม field ใน `MemberService.php` + `UserRepository.php`

รายละเอียดดูได้ใน `ARCHITECTURE.md` หัวข้อ 7 (แนวทางการต่อยอด)

### Q: ใช้ร่วมกับ frontend/framework อื่นได้ไหม?

**A:** ได้ครับ เพราะ Service Layer ของระบบแยกจาก UI อย่างชัดเจน:

- **ใช้กับ React / Vue / Angular:** สร้าง API Controller ใหม่ (ไฟล์ใน `api/`) → เรียก Service เดิมได้เลย → เปลี่ยน output จาก HTML เป็น JSON
- **ย้ายไป Laravel:** หลักการเดียวกัน (Service → Repository) แค่ย้ายไปอยู่ในโครงสร้าง Laravel
- **ใช้เป็นแนวทาง:** เรียนรู้จาก PHP ล้วนก่อน → ไป framework จะง่ายขึ้นมาก

### Q: ถ้าโค้ดรันไม่ได้ต้องทำยังไง?

1. **เปิด `APP_DEBUG=true`** ในไฟล์ `.env` → refresh หน้าเว็บ → จะเห็น error จริงขึ้นมา
2. **เช็ค 3 สาเหตุที่พบบ่อยที่สุด:**
   - ยังไม่ได้สร้างไฟล์ `.env` (ต้อง copy จาก `.env.example`)
   - ยังไม่ได้รัน `install.php` (ฐานข้อมูลยังไม่ถูกสร้าง)
   - Apache หรือ MySQL ใน XAMPP ยังไม่ได้เปิด
3. **ถ้ายังแก้ไม่ได้:** ส่ง screenshot error + บอกว่าแก้โค้ดอะไรไปบ้าง (หรือยังไม่ได้แก้) มาให้ผู้ขายดู

- ✅ "หลัง install เสร็จ login ไม่ได้ เจอ error นี้ [screenshot] ยังไม่ได้แก้โค้ดอะไรเลย"

## ⚠️ 9. ข้อจำกัดของสินค้า

### Q: หนังสือที่คนจองไว้แล้วไม่มารับ ทำไมยังไม่กลับขึ้นชั้น?

**A:** ระบบปล่อยการจองที่หมดอายุ **ตอนที่มีคนเปิดหน้าเว็บ** ไม่ใช่ปล่อยเองตามเวลา

เปิดหน้าไหนก็ได้ในกลุ่มนี้แล้วมันจะเคลียร์ให้ทันที:
**หน้าภาพรวม · รายการจอง · รายการหนังสือ · หน้าแรกฝั่งสมาชิก**

(แค่มีสมาชิกคนเดียวเปิดเว็บเข้ามาดูหนังสือ ระบบก็เคลียร์ให้แล้ว ไม่ต้องรอเจ้าหน้าที่)

- ปกติไม่มีใครสังเกตเห็น เพราะงานหน้าเคาน์เตอร์เปิดหน้าพวกนี้อยู่แล้วทั้งวัน
- จะเห็นผลก็ต่อเมื่อ **ห้องสมุดปิดยาวโดยไม่มีใครเปิดคอมเลย** — ปิด 5 วัน
  หนังสือที่คนจองไม่มารับก็ถูกกันไว้ 5 วัน พอเปิดคอมวันแรกก็คืนขึ้นชั้นครบทันที
- **ไม่มีข้อมูลหาย** และสต็อกไม่เคยเพี้ยน — แค่ปล่อยช้ากว่ากำหนดไปตามจำนวนวันที่ปิด

**🧠 ทำไมออกแบบแบบนี้:** การปล่อยตรงเวลาต้องใช้ cron ซึ่งลูกค้ากลุ่มเป้าหมาย
(ห้องสมุดที่ดูแลคนเดียว ไม่มีฝ่าย IT) ตั้งเองมักไม่เป็น
ถ้าออกแบบให้ *ต้อง* ตั้งแล้วเขาตั้งไม่เป็น ระบบจะพังเงียบโดยไม่มีใครรู้
**กลไกที่ช้าไปสองสามวันแต่ทำงานถูกเสมอ ดีกว่ากลไกที่ทำงานบ้างไม่ทำงานบ้าง**

**✅ ถ้าอยากให้ปล่อยตรงเวลา:** มีสคริปต์ `cron/expire_reservations.php` ให้แล้ว
ตั้งเป็นงานอัตโนมัติทุก 15 นาทีได้ (วิธีตั้งอยู่ใน `DEPLOYMENT.md` หัวข้อ Cron Jobs)
เป็นของแถมให้ดีขึ้น ไม่ตั้งก็ใช้งานได้ครบเหมือนเดิม

### Q: ไม่เหมาะกับระบบแบบไหน?

**A:**

| ระบบ | ทำไมไม่เหมาะ |
|-----|-------------|
| **ห้องสมุดขนาดใหญ่** (หลายพันคนพร้อมกัน) | ไม่มี caching, queue, horizontal scaling |
| **ระบบ enterprise** ที่ต้อง uptime สูง | เป็น single server ไม่มี failover |
| **ระบบ multi-tenant** (หลายห้องสมุดในระบบเดียว) | ออกแบบ single library เท่านั้น |
| **E-commerce / ระบบจ่ายเงินจริง** | ไม่มี payment gateway |
| **SPA + API only** | Controller สร้าง HTML inline (แต่ต่อยอดเป็น API ได้) |

### Q: ไม่ควรคาดหวังอะไรจาก template นี้?

**A:** เพื่อความเข้าใจที่ตรงกัน:

- ❌ ไม่ใช่ **software สำเร็จรูประดับองค์กร** — เป็น template สำหรับเรียนรู้และต่อยอด
- ❌ ไม่มี **การแจ้งเตือนผ่าน email/LINE** — ตั้งใจไม่ทำ เพราะเมลจากเครื่องลูกค้าจะลงถังสแปม
  ✅ ทดแทนด้วย **ใบรายชื่อโทรตามก่อนครบกำหนด** พร้อมเบอร์โทร กดโทรจากมือถือได้เลย
  และปุ่ม **จดว่าโทรแล้ว** — วางสายแล้วจดผลไว้ พรุ่งนี้ไม่ต้องไล่ใหม่ทั้งใบ
- ❌ ไม่มี **mobile app** — เป็นเว็บเท่านั้น (responsive ใช้มือถือเปิดได้ แต่ไม่ใช่ app)
- ❌ ไม่มี **multi-language** — ภาษาไทย + อังกฤษบางส่วน
- ❌ ไม่รับประกัน **ทำงานได้ 100% ในทุก environment** — ทดสอบบน XAMPP + MySQL
- ❌ ไม่มี **ซัพพอร์ตตลอดชีพ** — support 30 วัน

สิ่งเหล่านี้ไม่ใช่ข้อบกพร่อง แต่เป็น **ขอบเขตที่ออกแบบไว้** สำหรับ template ถ้าต้องการฟีเจอร์เหล่านี้ สามารถพัฒนาต่อเองได้จากฐานที่มี
