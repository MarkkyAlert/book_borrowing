# KNOWN LIMITATIONS

> ข้อจำกัดที่ **ยืนยันจากโค้ดจริง** — ใช้ตอบลูกค้าแบบไม่ขายเกินจริง

## 1. สถาปัตยกรรม / สเกล

| ข้อจำกัด | รายละเอียด |
|----------|-----------|
| Monolith เครื่องเดียว | ไม่มี failover / load balancer / cache layer |
| ค้นหา | **มี FULLTEXT แล้ว (F-24)** — ใช้ trigram เพราะ FULLTEXT ปกติค้นภาษาไทยไม่ได้ · ยังคง `LIKE` ไว้กรองซ้ำและเป็น fallback ดู §1.2 |
| ~~ไม่มี pagination~~ | **แก้แล้ว (F-21)** — แบ่งหน้าครบ 6 หน้าที่เคยโหลดทั้งชุด (`index.php`, `admin/books`, `borrows`, `members`, `payments`, `reservations`) ดู §1.1 |

## 1.1 รับได้กี่เล่ม — วัดจริงแล้ว 🧪 (อัปเดตหลังทำ pagination)

### แปลเป็นคำแนะนำ

| ขนาดห้องสมุด | ใช้ได้ไหม |
|--------------|-----------|
| **≤ 2,000 เล่ม** | สบาย — วัดจริงแล้ว หน้าเว็บ 62 KB โหลด 0.32 วินาที |
| **2,000–10,000 เล่ม** | คาดว่ายังสบาย เพราะขนาดหน้าคงที่ · จุดที่จะเริ่มช้าคือ SQL `LIKE '%คำ%'` ซึ่งที่ 2,000 แถวใช้ 10.7 ms |
| **> 10,000 เล่ม** | ต้องทำ **FULLTEXT index** แทน `LIKE '%คำ%'` (ยังไม่ได้ทำ) · ควรวัดซ้ำก่อนรับปาก |

⚠️ ตัวเลขวัดบน **localhost ที่ไม่มี network latency** — แต่ตอนนี้ขนาดหน้าอยู่ระดับหลักสิบ KB
จึงไม่ใช่ปัญหาบนเน็ตช้าหรือมือถืออีกต่อไป (เดิม 5.5 MB บนเน็ต 10 Mbps = รอโหลดเพิ่ม ~4 วินาที)

(ยิงซ้ำ 5 รอบที่ 50 และ 75 → ไม่มี error เลย · ที่ 100 → 1 ใน 5 รอบ p95 เกิน 1 วินาที)

— ทดสอบไว้แค่ระดับ 2 คนแย่งเล่มสุดท้าย (ดู F-20) · ชุดนี้ยิงเฉพาะ request แบบอ่าน

## 1.2 การค้นหา — ทำ FULLTEXT แล้ว (F-24)

> 🔴 **สิ่งที่ต้องรู้ก่อนแตะโค้ดค้นหา:** FULLTEXT ของ MySQL/MariaDB ตัดคำด้วยช่องว่าง
> ภาษาไทยไม่มีช่องว่าง → ใส่ FULLTEXT บน `title` ตรง ๆ แล้ว **ค้นคำกลางชื่อเรื่องไม่เจอ**
> (ทดสอบยืนยันแล้ว) ระบบจึงใช้ **คอลัมน์เงาแบบ trigram** `books.search_tokens` แทน
> รายละเอียดครบใน FINDINGS.md F-24

วัดผ่าน `BookRepository::countAll()` ที่ **21,229 เล่ม** — ผลลัพธ์ตรงกับ `LIKE` เดิมทุกเคส:

| คำค้น | จำนวนผล | LIKE (ก่อน) | FULLTEXT | เร็วขึ้น |
|-------|---------|-------------|----------|---------|
| `ปัญญาประดิษฐ์` | 500 | 25.9 ms | 14.9 ms | 1.7× |
| `สมุนไพร` | 500 | 24.0 ms | 13.0 ms | 1.8× |
| `ณัฐพล` (ไม่มีในระบบ) | 0 | 32.7 ms | 6.9 ms | **4.7×** |
| `Atomic` | 1 | 18.8 ms | 7.1 ms | 2.7× |
| `9789740000000` (ISBN) | 0 | 21.1 ms | 19.6 ms | 1.1× |

ยิ่งค้นแล้วเจอน้อย ยิ่งได้ประโยชน์ — ซึ่งเป็นกรณีที่เจอบ่อยที่สุด (พิมพ์ผิด, หาเล่มที่ไม่มี)

**⚠️ ไม่ได้เร็วขึ้นทุกกรณี:**

| กรณี | ผล |
|------|-----|
| ค้นด้วยตัวเลข (ISBN) | trigram ตัวเลขมีแค่ 1,000 แบบ → ไม่เจาะจงพอ · ระบบข้ามไปใช้ LIKE เมื่อคำค้นเป็นตัวเลขเกิน 70% |
| คำค้นสั้นกว่า 3 ตัวอักษร | ใช้ FULLTEXT ไม่ได้เลย (`innodb_ft_min_token_size`) → ตกไปใช้ LIKE |
| ข้อมูลที่ชื่อซ้ำกันแทบทั้งตาราง | FULLTEXT ช้ากว่า LIKE (ห้องสมุดจริงไม่เป็นแบบนี้ แต่ชุดข้อมูล `seed_bulk_data.php` เป็น) |
| ≤ 2,000 เล่ม | แทบไม่ต่าง — `COUNT` ใช้ ~10 ms อยู่แล้ว |

**🔴 ภาระที่ตามมา:** `books.search_tokens` **PHP เป็นคนสร้าง** ไม่ใช่ trigger
(สร้าง stored function ไม่ได้บนเครื่องนี้ — `mysql.proc` พังจากการอัปเกรดที่ไม่ได้รัน `mysql_upgrade`)
→ หนังสือที่ถูก `INSERT` ด้วย SQL ตรง ๆ จะ **ค้นหาไม่เจอ** จนกว่าจะรัน:

```bash
php database/rebuild_search_index.php
```

ตรวจว่ามีเล่มตกหล่นไหมด้วย `--check` (ชุดทดสอบเรียกให้อยู่แล้วผ่าน SI-08)

**สิ่งที่ยังไม่ได้ทำ:** จัดอันดับความเกี่ยวข้อง (relevance ranking) — ตอนนี้เรียงตามวันที่เพิ่ม
เหมือนเดิม ไม่ได้เรียงตาม "ตรงมากที่สุดก่อน"
| ไม่ใช่ real-time | ไม่มี WebSocket/SSE — หลายเครื่องเห็นตรงกันเพราะใช้ **DB กลางชุดเดียว** ต้อง reload เอง |
| Session เก็บใน filesystem | scale หลาย server ต้องย้ายไป Redis/DB เอง |
| ไม่มี multi-tenant / หลายสาขา | เพิ่มทีหลัง = เปลี่ยน data model ครั้งใหญ่ |
## 2. ✅ ใช้งานออฟไลน์ได้ (แก้แล้ว — F-09)

**ระบบไม่พึ่งอินเทอร์เน็ตแล้ว** ไลบรารีทั้งหมดเก็บไว้ใน `assets/vendor/` (1.8 MB)
เดิมโหลดจาก CDN 4 แหล่ง ซึ่งทำให้ห้องสมุด intranet **ติดตั้งแล้วใช้งานไม่ได้เลย**

| ไลบรารี | ใช้ที่ไหน | เก็บไว้ที่ |
|---------|-----------|-----------|
| Tailwind (Play CDN) | ทุกหน้า | `assets/vendor/tailwind/` |
| Bootstrap 5.3.2 + Icons 1.11.1 | หน้า admin, install | `assets/vendor/bootstrap*/` |
| ฟอนต์ Sarabun 300–700 | ทุกหน้า | `assets/vendor/fonts/` |
| Chart.js | Dashboard | `assets/vendor/chartjs/` |
| Select2 4.1.0-rc.0 | ฟอร์มยืม | `assets/vendor/select2/` |
| flatpickr + locale ไทย | เลือกช่วงวันในรายงาน | `assets/vendor/flatpickr/` |
| JsBarcode 3.11.0 | ฉลากหนังสือ + บัตรสมาชิก | `assets/vendor/jsbarcode/` |
| QRCode.js 1.0.0 | บัตรสมาชิก | `assets/vendor/qrcode/` |

ยืนยันแล้วด้วยเบราว์เซอร์จริง: `performance.getEntriesByType('resource')` **external = 0** ทุกหน้า
· ชุดทดสอบ Suite 2e กันไม่ให้มีใครเผลอเพิ่ม CDN กลับเข้ามา

**⚠️ ยังใช้ Tailwind แบบคอมไพล์ในเบราว์เซอร์ (Play CDN)** ซึ่งผู้พัฒนา Tailwind
ระบุว่าไม่เหมาะกับ production — หน้าเว็บต้องโหลด JS 400 KB แล้วคอมไพล์ CSS ตอนเปิดทุกครั้ง
จงใจคงไว้เพราะเปลี่ยนเป็น CSS นิ่งต้องเพิ่ม Node/npm เข้ามาในโปรเจกต์ที่ตั้งใจไม่มี build step
ถ้ายอมรับการเพิ่ม build step ได้ ตรงนี้คือจุดที่ปรับให้เบาลงได้มากที่สุด

## 4. ข้อจำกัดเชิงข้อมูล

- **ลบหนังสือ/สมาชิกที่มีประวัติไม่ได้** (ตั้งใจ — FK RESTRICT + guard ใน Service) วิธีที่ถูกคือซ่อนด้วย `is_visible`
- **ไม่มี soft delete สำหรับสมาชิก** — มีแค่หนังสือที่ซ่อนได้
- **ไม่มี audit trail** — รู้แค่ `payments.recorded_by` ว่าใครรับเงิน ไม่รู้ว่าใครแก้ข้อมูลหนังสือ/สมาชิก
- **ไม่มีประวัติการเปลี่ยน stock** — รู้แค่ค่าปัจจุบัน
- ~~**`reservations` ไม่มี UNIQUE กัน pending ซ้ำ**~~ → ✅ **แก้แล้ว 2026-08-29** พร้อม ROADMAP ข้อ 5 — `uq_reservation_active (user_id, book_id, active_slot)` โดย `active_slot` เป็นคอลัมน์ generated ที่เป็น 1 เมื่อสถานะเป็น `waiting`/`pending` และเป็น NULL เมื่อการจองปิดแล้ว (MySQL มอง NULL ว่าไม่ชนกัน) จึงกันซ้ำเฉพาะการจองที่ยังมีชีวิต และยังจองเล่มเดิมใหม่ได้หลังคืน
- **หน้าลืมรหัสผ่านยังมีช่องทางเวลาเหลืออยู่เล็กน้อย** — คำตอบและหน้าจอเหมือนกันทุกกรณีแล้ว
  (อีเมลมีจริง/ไม่มี/เกินโควตา) แต่ฝั่งที่ได้ token จริงมี `INSERT` เพิ่ม 1 ครั้ง
  ทำให้เวลาตอบสนองต่างกันในระดับมิลลิวินาที · วัดผ่าน HTTP ได้ยากมากเพราะเวลา render
  กลบไปหมด และตัวจำกัดอัตราระดับ IP คุมจำนวนครั้งไว้อยู่แล้ว · ถ้าลูกค้าต้องการปิดสนิท
  ต้องทำงานหลอกให้เท่ากันทั้ง 2 ฝั่ง ซึ่งแลกกับความซับซ้อนที่ไม่คุ้มในระดับนี้
- **ระบบไม่ส่งอีเมล** — ไม่มีค่า MAIL/SMTP ใน `.env` และไม่มีการเรียกฟังก์ชันส่งเมล
  หน้าลืมรหัสผ่านจึงบอกให้ติดต่อเจ้าหน้าที่ให้ตั้งรหัสผ่านใหม่แทน (ทำได้จริงจากหน้าแก้ไขสมาชิก)
  ถ้าลูกค้าต่อ SMTP ทีหลัง ตาราง `password_resets` และ `reset_password.php` พร้อมใช้อยู่แล้ว
- **ค่าปรับเก็บเป็น `DECIMAL(10,2)` แต่ `FINE_PER_DAY` เป็น int** — ค่าปรับเศษสตางค์ทำไม่ได้จาก config

## 5. ข้อจำกัดของ Idempotency / Concurrency

- Idempotency key เก็บใน **session** (อายุ 5 นาที) — กัน double-submit ได้เฉพาะ session เดียวกัน
- คนละเครื่อง/คนละ session ยิงพร้อมกัน → พึ่ง row lock + UNIQUE constraint (ซึ่งทดสอบแล้วว่าทำงาน)
- `checkRateLimit()` เป็น **fail-open** ถ้า DB ล่ม
