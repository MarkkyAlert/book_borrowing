# 📋 LIMITATIONS.md — ขอบเขตการใช้งานระบบยืมคืนหนังสือ

> เอกสารนี้อธิบาย **ขอบเขตของ template** อย่างตรงไปตรงมา
> เพื่อให้ผู้ซื้อเข้าใจว่า "ออกแบบมาเพื่ออะไร" และ "ไม่ได้ออกแบบมาเพื่ออะไร"
> การรู้ขอบเขตล่วงหน้าจะช่วยให้ใช้งานได้อย่างเต็มประสิทธิภาพ

---

## 🎯 1. วัตถุประสงค์ของ Template นี้

### ออกแบบมาเพื่ออะไร?

Template นี้ถูกสร้างขึ้นเพื่อเป็น **ระบบยืมคืนหนังสือบนเว็บที่ทำงานได้จริง** พร้อมโครงสร้างที่ชัดเจนและเอกสารประกอบครบถ้วน โดยมีวัตถุประสงค์หลัก:

- **เรียนรู้ PHP Backend** — เห็นโครงสร้าง Layered Architecture จริงๆ ไม่มี framework ซ่อน
- **เรียนรู้ Security** — มีตัวอย่าง CSRF, XSS, SQL Injection prevention, Rate Limiting, Row Locking ของจริง
- **ส่งงาน / ส่ง Project** — ระบบครบ ฟีเจอร์ครบ มี comment ภาษาไทยอธิบายทุกจุดสำคัญ
- **เดโมระบบ** — ติดตั้งง่ายด้วย XAMPP กดปุ่มเดียว พร้อมข้อมูลตัวอย่าง
- **ใช้งานจริงในขนาดเล็ก** — ห้องสมุดหรือร้านที่มีสมาชิกไม่กี่ร้อยคน
- **เป็นฐานในการต่อยอด** — โครงสร้างแยกชั้นชัดเจน เพิ่ม Service/Repository ใหม่ได้ง่าย

### กลุ่มเป้าหมายหลัก

| กลุ่ม | ใช้ทำอะไร |
|-------|---------|
| **นักศึกษา** | ส่งโปรเจคจบ, รายงาน, ฝึกปฏิบัติ |
| **ผู้เริ่มต้นเรียน Backend** | เข้าใจ architecture, security, transaction |
| **ผู้สอน** | ใช้เป็นตัวอย่างสอนนักเรียน |
| **Freelancer** | ใช้เป็น template ต่อยอดงานให้ลูกค้า |
| **ห้องสมุด/ร้านขนาดเล็ก** | ระบบยืมคืนบนเว็บ สมาชิกไม่เกินไม่กี่ร้อยคน |

## 🚫 2. สิ่งที่ Template นี้ "ไม่ได้ออกแบบมาเพื่อ"

Template นี้มีขอบเขตที่ชัดเจน สิ่งต่อไปนี้ **ไม่ใช่เป้าหมายของการออกแบบ**:

### ไม่ได้ออกแบบสำหรับระบบขนาดใหญ่

- ไม่เหมาะกับห้องสมุดมหาวิทยาลัยที่มีนักศึกษาหลายหมื่นคน
- ไม่เหมาะกับระบบที่ต้องรองรับผู้ใช้หลายร้อยคนพร้อมกัน
- ไม่เหมาะกับองค์กรที่มีหลายสาขา (multi-tenant)

### ไม่ได้ออกแบบสำหรับ High Availability

- ไม่มีระบบ failover (ถ้า server ล่ม ระบบจะหยุดทำงาน)
- ไม่มี load balancer
- ไม่รับประกัน uptime ระดับ 99.9% หรือสูงกว่า
- ไม่มี SLA (Service Level Agreement) ใดๆ

### ไม่ได้ออกแบบสำหรับ Enterprise

- ไม่มีระบบ audit trail ระดับองค์กร
- ไม่มี compliance certification (ISO 27001, PCI-DSS, PDPA ระดับองค์กร)
- ไม่มีระบบ role permission ที่ปรับแต่งได้ละเอียด (มีแค่ 3 role: admin, staff, member)
- ไม่มีระบบ approval workflow หลายขั้น

### ไม่ได้ออกแบบสำหรับ E-commerce

- ไม่มี payment gateway
- ไม่มีระบบจ่ายเงินออนไลน์
- ค่าปรับในระบบเป็นการบันทึกรับเงินสด ไม่ใช่การชำระผ่านระบบ

## ⚙️ 3. ข้อจำกัดด้านสถาปัตยกรรม

### โครงสร้างปัจจุบัน

ระบบใช้ **Layered Architecture (Monolith)** แบบ vanilla PHP:

```
Controller → Service → Repository → Database (MySQL)
```

นี่คือโครงสร้างที่ **เหมาะกับการเรียนรู้และระบบขนาดเล็ก** แต่มีขอบเขตดังนี้:

| ด้าน | สถานะปัจจุบัน | หมายเหตุ |
|------|-------------|---------|
| **สถาปัตยกรรม** | Monolith (ทุกอย่างอยู่ใน project เดียว) | เหมาะกับ single server |
| **Microservices** | ยังไม่รองรับ | ต้อง refactor ถ้าต้องการ |
| **Queue / Background Job** | ยังไม่มี | ทุกอย่างทำงานแบบ synchronous |
| **Auto-scaling** | ยังไม่มี | ออกแบบสำหรับ single server |
| **API Gateway** | ยังไม่มี | มี API endpoint พื้นฐาน 5 ตัว |
| **WebSocket / Real-time** | ยังไม่มี | ต้องเพิ่มเองถ้าต้องการ |
| **Multi-database** | ยังไม่รองรับ | ใช้ MySQL ตัวเดียว |

### Session Management

- ใช้ PHP file-based session (default) → ไม่รองรับ multi-server
- ถ้าต้องการ multi-server → ต้องเปลี่ยนเป็น Redis/Database session

### Reservation Expiry

- ใช้ **Lazy Expire** (ตรวจตอนเปิดหน้าเว็บ) → ไม่มี cron job อัตโนมัติ
- ถ้าไม่มีคนเปิดหน้าเว็บเลย จองที่หมดอายุจะยังไม่ถูกคืน stock
- มีไฟล์ `cron/expire_reservations.php` ให้ตั้ง cron เพิ่มเองได้

## 🔐 4. ข้อจำกัดด้านความปลอดภัย

### สิ่งที่มีอยู่แล้ว (พื้นฐานที่ดี)

ระบบมีมาตรการความปลอดภัยหลายชั้นที่ทำงานจริง:

| มาตรการ | ป้องกันอะไร | อยู่ชั้นไหน |
|---------|-----------|----------|
| ✅ **Prepared Statements (native)** | SQL Injection | Repository |
| ✅ **`e()` output escaping** | XSS | Controller |
| ✅ **CSRF Token ทุก form** | CSRF | Controller |
| ✅ **bcrypt password hashing** | รหัสผ่านรั่วไหล | Service/Helper |
| ✅ **Rate Limiting** | Brute force login | Controller |
| ✅ **Session regeneration** | Session fixation | Controller |
| ✅ **HttpOnly + SameSite cookies** | Session hijacking | Config |
| ✅ **Row Locking (FOR UPDATE)** | Race condition | Repository |
| ✅ **WHERE guard clauses** | Stock ติดลบ | Repository |
| ✅ **IDOR prevention** | เข้าถึงข้อมูลคนอื่น | Service |
| ✅ **Idempotency keys** | กดซ้ำ | Controller |
| ✅ **บังคับเปลี่ยนรหัสผ่านครั้งแรก** | รหัสเริ่มต้นร่วมที่ทุกคนรู้ | Controller/Service |
| ✅ **ไม่บอกว่าอีเมลไหนมีในระบบ** | การไล่เดารายชื่อสมาชิก | Controller |
| ✅ **บังคับเปลี่ยนรหัสที่ผู้ดูแลตั้งให้** | รหัสที่คนอื่นรู้ถูกใช้ต่อไปเรื่อย ๆ | Repository |

### สิ่งที่ยังไม่มี (ขอบเขตที่ยังไม่ครอบคลุม)

| ด้าน | สถานะ | หมายเหตุ |
|------|-------|---------|
| **HTTPS บังคับ** | Config พร้อม แต่ยังไม่บังคับ | ต้องตั้ง SSL certificate เอง |
| **Penetration Testing** | ยังไม่ได้ทำ | ควรทำถ้าจะใช้ production จริงจัง |
| **Security Audit ภายนอก** | ยังไม่ได้ทำ | ต้องจ้างผู้เชี่ยวชาญแยก |
| **ISO 27001 / PCI-DSS** | ไม่มี certification | ต้องดำเนินการเองตามมาตรฐาน |
| **PDPA compliance ระดับองค์กร** | ยังไม่ครอบคลุม | มีพื้นฐาน (hash password, ไม่ log sensitive data) แต่ไม่ครบตามกฎหมาย |
| **2FA (Two-Factor Authentication)** | ยังไม่มี | ต้องเพิ่มเองถ้าต้องการ |
| **IP Whitelisting** | ยังไม่มี | ต้องตั้ง server-level เอง |
| **WAF (Web Application Firewall)** | ยังไม่มี | ต้องตั้ง infrastructure-level เอง |
| **Content Security Policy** | ยังไม่มี | ต้องเพิ่ม HTTP headers เอง |

> 💡 **สรุป:** มาตรการ security ที่มี **เพียงพอสำหรับการเรียนรู้และใช้งานขนาดเล็ก** แต่ถ้าจะใช้ production ที่มีข้อมูลสำคัญ ควรเพิ่มมาตรการตามที่ระบุข้างต้น

## 📈 5. ข้อจำกัดด้าน Performance

### ออกแบบมาสำหรับ traffic ระดับไหน?

| สถานการณ์ | ทำงานได้ดีหรือไม่ |
|---------|---------------|
| สมาชิก 100-500 คน เข้าทีละ 5-10 คน | ✅ ทำงานได้ดี |
| ผู้ใช้พร้อมกัน 10-30 คน | ✅ ทำงานได้ดี |
| ผู้ใช้พร้อมกัน 50-100 คน | ⚠️ อาจช้าลง ขึ้นกับ server |
| ผู้ใช้พร้อมกัน 100+ คน | ❌ เกินขอบเขตที่ออกแบบไว้ |

### สิ่งที่ยังไม่มีด้าน Performance

| ด้าน | สถานะ | ผลกระทบ |
|------|-------|--------|
| **Application Caching** | ยังไม่มี (Redis/Memcached) | ทุก request query DB ใหม่ |
| **Query Optimization ขั้นสูง** | ใช้ index พื้นฐาน | เพียงพอสำหรับข้อมูลไม่เกินหมื่น records |
| **CDN** | ยังไม่มี | ไฟล์ static serve จาก server ตรง |
| **Image Optimization** | เก็บรูปปกตามขนาดที่อัปโหลด | ไม่มี resize/compress อัตโนมัติ |
| **Connection Pooling** | ใช้ PDO connection เดียวต่อ request | เพียงพอสำหรับ traffic ต่ำ-กลาง |
| **Stress Testing** | ยังไม่ได้ทำ | ไม่มีตัวเลข benchmark อ้างอิง |
| **Database Read Replica** | ยังไม่มี | ใช้ DB ตัวเดียวทั้ง read/write |

### Rate Limiting

- เก็บข้อมูล Rate Limit ใน MySQL → ทำงานได้ดีสำหรับ traffic ต่ำ
- ถ้า traffic สูง → ควรย้ายไป Redis (เร็วกว่ามาก)

> 💡 **สรุป:** Performance ที่มี **เพียงพอสำหรับห้องสมุดขนาดเล็กและการเรียนรู้** ถ้าต้องการ traffic สูง ต้องเพิ่ม caching, CDN, connection pooling ตามความจำเป็น

## 🧩 6. ข้อจำกัดด้านฟีเจอร์

| หมวด | ฟีเจอร์ |
|------|--------|
| **หนังสือ** | เพิ่ม, แก้ไข, ลบ, นำเข้า CSV, อัปโหลดปก, จัดหมวดหมู่, **เลขเรียกหนังสือ**, **หนังสืออ้างอิง (ห้ามยืม)**, **พิมพ์ฉลากบาร์โค้ดติดสัน** |

| **จอง** | จองออนไลน์, อนุมัติ, ยกเลิก, หมดอายุอัตโนมัติ, **จองรอคิวเมื่อถูกยืมหมด** |

| **ตั้งค่าจากหน้าเว็บ** | **กฎการยืม-คืน 9 ข้อ** (วันยืม · โควตาแยกสมาชิก/เจ้าหน้าที่ · ค่าปรับ · จำนวนครั้งที่ต่ออายุได้ · ค่าดำเนินการหนังสือหาย · วงเงินยกเว้นของเจ้าหน้าที่ · วันหมดอายุการจอง · **เตือนใกล้ครบกำหนดล่วงหน้ากี่วัน**), **วันที่ห้องสมุดปิด**, บัตรสมาชิก |

### ฟีเจอร์ที่ยังไม่มี

#### 🔴 สามข้อนี้กระทบงานประจำ — อ่านก่อนตัดสินใจซื้อ

| ฟีเจอร์ | ความจริง และผลที่ตามมา |

| **ส่งอีเมลได้เฉพาะลิงก์รีเซ็ตรหัสผ่าน (ปิดไว้เป็นค่าเริ่มต้น)** | ตั้งค่า SMTP ได้ที่หน้าตั้งค่าระบบ พร้อมปุ่ม **ทดสอบส่งเมล** · ไม่ตั้งค่าก็ใช้ระบบได้ครบเหมือนเดิม<br>🔴 **ไม่มีการแจ้งเตือนใกล้ครบกำหนด/เกินกำหนดทางอีเมล และตั้งใจไม่ทำ**<br>🧠 **เหตุผลที่ไม่ทำ:** เมลที่ส่งจากเครื่องลูกค้าซึ่งไม่มีโดเมน/SPF/DKIM ของตัวเองจะถูกตีกลับหรือลงถังสแปมเงียบ ๆ บรรณารักษ์จะเลิกไล่ตามด้วยมือเพราะคิดว่าระบบเตือนให้แล้ว → หนังสือหายมากกว่าเดิม · **ระบบเตือนที่ทำงานบ้างไม่ทำงานบ้างโดยไม่มีใครรู้ แย่กว่าการไม่มีแล้วบอกตรง ๆ** · ยังไม่นับว่า Gmail ต้องใช้ App Password ซึ่งบรรณารักษ์ตั้งเองไม่ได้ และการเตือนล่วงหน้าต้องใช้ cron ที่ลูกค้ากลุ่มนี้มักตั้งไม่เป็น<br>✅ **ทดแทนด้วย:** ① **ใบรายชื่อโทรตามก่อนครบกำหนด** — หน้าภาพรวมขึ้นรายชื่อพร้อมเบอร์โทรกดโทรได้ พิมพ์เป็นใบไปนั่งโทรได้ และมีปุ่ม **จดว่าโทรแล้ว** ให้บันทึกวันที่+ผลการโทร (เก็บครั้งล่าสุดครั้งเดียว ไม่ใช่ประวัติทุกสาย) ช่องนี้จะว่างบนใบที่พิมพ์ถ้ายังไม่เคยโทร ไว้เขียนมือได้ ② **ผู้ดูแลตั้งรหัสผ่านให้ที่เคาน์เตอร์** ระบบบังคับให้สมาชิกตั้งรหัสใหม่ทันทีที่เข้าใช้ ผู้ดูแลจึงไม่ค้างรู้รหัสของใคร<br>⚠️ ที่ยังขาดจริง ๆ คือ **สมาชิกรีเซ็ตรหัสเองจากที่บ้านไม่ได้** ต้องเดินมาที่ห้องสมุด · หน้า "ลืมรหัสผ่าน" แสดงลิงก์รีเซ็ตบนจอ **เฉพาะตอนรันบน localhost และเปิด `APP_DEBUG=true`** เท่านั้น |
| **การจองหมดอายุถูกปล่อยตอนมีคนเปิดหน้า ไม่ใช่ปล่อยเองตามเวลา** | เมื่อเลยกำหนดมารับ (ค่าเริ่มต้น 2 วัน) การจองจะถูกเปลี่ยนเป็น "หมดอายุ" และหนังสือกลับขึ้นชั้น — **แต่เกิดขึ้นตอนที่มีคนเปิดหน้าที่เกี่ยวกับการจองเท่านั้น** (หน้าภาพรวม / รายการจอง / รายการหนังสือ / หน้าแรกฝั่งสมาชิก — แค่มีสมาชิกเปิดเว็บดูหนังสือก็เคลียร์ให้แล้ว)<br>⚠️ **ผลจริง:** ห้องสมุดปิดยาวโดยไม่มีใครเปิดคอมเลย 5 วัน หนังสือที่คนจองไม่มารับจะถูกกันไว้ตลอด 5 วันนั้น พอเปิดคอมวันแรกก็คืนขึ้นชั้นครบทันที<br>🧠 **เหตุผลที่ไม่ทำเป็นงานอัตโนมัติตามเวลา:** ต้องใช้ cron ซึ่งลูกค้ากลุ่มนี้ตั้งเองมักไม่เป็น · ถ้าออกแบบให้ *ต้อง* ตั้งแล้วเขาตั้งไม่เป็น ระบบจะพังเงียบโดยไม่มีใครรู้ · **การปล่อยช้าไปสองสามวันแล้วยังทำงานถูกเสมอ ดีกว่ากลไกที่ทำงานบ้างไม่ทำงานบ้าง**<br>✅ **ถ้าอยากให้เร็วขึ้น:** มีสคริปต์ `cron/expire_reservations.php` ให้แล้ว ตั้งเป็นงานอัตโนมัติทุก 15 นาทีได้ (วิธีตั้งอยู่ใน `DEPLOYMENT.md` หัวข้อ Cron Jobs) — เป็นของแถม ไม่ตั้งก็ไม่มีอะไรหาย |
| **สมาชิกที่ไม่มีอีเมล รีเซ็ตรหัสผ่านเองไม่ได้** | เว้นช่องอีเมลตอนเพิ่มสมาชิกได้แล้ว (ผู้สูงอายุ/เด็กเล็กที่ไม่มีอีเมลจริง) ระบบตั้งรหัสประจำตัวให้เป็น `m{รหัสสมาชิก}@local.invalid` ใช้ล็อกอินได้ปกติ<br>🔴 แต่ส่งเมลไปที่อยู่นี้ไม่ได้ (โดเมน `.invalid` สงวนไว้ไม่ให้จดจริงตาม RFC 2606) ระบบจึง **ไม่ออกลิงก์รีเซ็ตให้** — ลืมรหัสต้องมาที่เคาน์เตอร์ให้เจ้าหน้าที่ตั้งใหม่<br>🧠 การสมัครเองผ่านหน้าเว็บสาธารณะยัง **บังคับกรอกอีเมล** เพราะคนที่สมัครออนไลน์จะไม่รู้รหัสประจำตัวที่ระบบตั้งให้ กลายเป็นบัญชีที่เจ้าตัวเข้าไม่ได้ |
| **นำเข้าสมาชิกที่ไม่มีอีเมล ซ้ำได้** | อีเมลคือกุญแจตัวเดียวที่ใช้ตัดสินว่า "คนนี้มีอยู่แล้ว" แถวที่เว้นช่อง Email จึงถือเป็นคนใหม่เสมอ<br>⚠️ นำเข้าไฟล์เดิมซ้ำอีกครั้งจะได้สมาชิกซ้ำ — ถ้าจะนำเข้าซ้ำ ควรใส่อีเมลให้ทุกแถว |
| **ลบสมาชิกที่เคยยืมไม่ได้ — ใช้ "เลิกใช้งาน" แทน** | ประวัติการยืมต้องอยู่ครบเพื่อทำสถิติสิ้นปี ระบบจึงห้ามลบ<br>✅ ปิดสวิตช์ "ยังใช้งานอยู่" ในหน้าแก้ไขสมาชิกแทน → หายจากรายชื่อตอนบันทึกการยืม และเข้าระบบไม่ได้ **แต่ประวัติยังอยู่ครบ และเจ้าหน้าที่ยังรับคืนหนังสือที่เขาค้างไว้ได้ตามปกติ** (ไม่งั้นหนังสือจะถูกขังอยู่กับคนที่ติดต่อไม่ได้) |
| **แจ้งเตือนผ่านกระดิ่งในหน้าเว็บ ไม่ใช่ push และไม่เรียลไทม์** | เจ้าหน้าที่เห็น: เกินกำหนดคืน · ครบกำหนดคืนวันนี้ · ใกล้ครบกำหนด · จองใกล้หมดอายุ · จองรอมารับ · ค้างชำระค่าปรับ และหมวด **สุขภาพระบบ** (สต็อกไม่ตรงกับการยืมจริง · ส่งอีเมลไม่สำเร็จ · อัปโหลดปกไม่ได้ · ยังไม่ได้ลบไฟล์ติดตั้ง · เปิดโหมดพัฒนาอยู่ — สองข้อหลังเห็นเฉพาะ admin) · สมาชิกเห็นของตัวเอง 6 อย่างเช่นกัน<br>🔴 **คำนวณตอนโหลดหน้าเท่านั้น ไม่มีการอัปเดตเอง** — เปิดแท็บทิ้งไว้แล้วตัวเลขจะไม่ขยับจนกว่าจะโหลดหน้าใหม่ กระดิ่งจึงติดป้าย **"ข้อมูล ณ HH:MM"** ไว้ให้เห็นว่าเลขนี้คำนวณเมื่อไหร่<br>🧠 **เหตุผลที่ไม่ทำ auto-refresh:** งานหน้าเคาน์เตอร์โหลดหน้าอยู่แล้วตลอด (ยืม คืน ค้นหา) · การ poll ทุก 30 วินาทีคือชิ้นส่วนที่พังเงียบได้ แล้วจะแสดงเลขเก่าโดยไม่บอกว่าเก่า ซึ่งแย่กว่าเลขที่นิ่งอยู่กับที่อย่างซื่อสัตย์ |
| **บาร์โค้ดผูกกับ "ชื่อเรื่อง" ไม่ใช่ "เล่ม"** | ยังไม่มีเลขทะเบียนรายเล่ม หนังสือชื่อเดียวกัน 5 เล่มใช้บาร์โค้ดเดียวกัน · ระบบรู้ว่าเหลือกี่เล่ม แต่บอกไม่ได้ว่า**เล่มไหน**หาย ชำรุด หรือใครถือเล่มไหนอยู่ · ห้องสมุดที่ต้องตรวจสอบรายเล่มยังใช้ไม่ได้<br>✅ **มีทางบรรเทา:** ช่อง **"หมายเหตุรายเล่ม"** ในหน้าแก้ไขหนังสือ ให้เจ้าหน้าที่จดเองว่าเล่มไหนเป็นอย่างไร (เช่น *เล่ม 2 ปกขาด · เล่ม 3 หาย 12 ส.ค.*) เป็นบันทึกภายใน สมาชิกไม่เห็น · **แต่เป็นสมุดจด ระบบไม่ได้หักสต็อกให้** ถ้าเล่มหายจริงต้องแก้ "จำนวนทั้งหมด" เอง |
| **ไม่มีบันทึกว่าใครทำอะไร (Activity Log)** | มีข้อมูลว่าใครยืมอะไรเมื่อไร แต่**ไม่มีบันทึกกลางว่าเจ้าหน้าที่คนไหนแก้ข้อมูลอะไร ยกเว้นค่าปรับให้ใคร หรือลบอะไรไป** · ห้องสมุดที่ต้องตรวจสอบย้อนหลังต้องเพิ่มเอง |

## 🛠️ 7. ความรับผิดชอบของผู้ใช้งาน

### ก่อนนำไปใช้งานจริง ผู้ซื้อควร:

**ศึกษาระบบก่อน:**
- อ่าน `README.md` เพื่อเข้าใจภาพรวม
- อ่าน `FLOW.md` เพื่อเข้าใจการทำงาน
- ทดสอบทุก flow ด้วยตัวเอง (ยืม, คืน, จอง, ค่าปรับ)

**ทดสอบใน environment ของตัวเอง:**
- ติดตั้งบน XAMPP/WAMP ทดสอบก่อน
- ตรวจว่าทำงานถูกต้องกับ PHP + MySQL version ที่ใช้
- ทดลองกับข้อมูลจริงของตัวเองก่อน deploy

**หากจะนำไปใช้ production:**
- เปลี่ยน `APP_DEBUG=false`
  ⚠️ หลังตั้งค่านี้ หน้า "ลืมรหัสผ่าน" จะไม่แสดงลิงก์รีเซ็ตอีก — เตรียมขั้นตอนให้ผู้ดูแล
  ตั้งรหัสให้สมาชิกที่เคาน์เตอร์ไว้ล่วงหน้า (ดูหัวข้อ 6)
- ลบไฟล์ `install.php`
- เปลี่ยนรหัสผ่าน admin (ระบบบังคับให้เปลี่ยนตอน login ครั้งแรกอยู่แล้ว)
- **ตั้งกฎการยืม-คืนที่หน้าตั้งค่าระบบให้ตรงกับระเบียบของห้องสมุด** — วันยืม โควตา ค่าปรับ
  (ตั้งที่หน้าเว็บ ไม่ใช่ `.env` · ค่าใน `.env` จะถูกทับทันทีที่กดบันทึกครั้งแรก)
- **ใส่วันหยุดประจำปีของห้องสมุดในหน้าตั้งค่า** ก่อนเริ่มให้ยืมจริง ไม่งั้นจะคิดค่าปรับวันที่ปิด
- **ตรวจว่าโฟลเดอร์ `uploads/covers/` เขียนได้** — ตัวติดตั้งจะเตือนถ้าเขียนไม่ได้ ห้ามข้าม
  ไม่งั้นอัปโหลดรูปปกไม่ได้ทั้งระบบ
- ตั้ง cron ให้ `cron/expire_reservations.php` ถ้าต้องการให้การจองหมดอายุเองโดยไม่ต้องรอคนเปิดเว็บ
- ตั้ง HTTPS
- ตั้ง backup ฐานข้อมูล
- พิจารณาเพิ่มมาตรการ security ตามหัวข้อ 4
- พิจารณาเพิ่ม performance ตามหัวข้อ 5

**หากจะแก้ไขโค้ด:**
- สำรองไฟล์เดิมก่อนแก้เสมอ (ใช้ Git หรือ copy)
- อ่าน `FLOW.md` หัวข้อ 6.6 (จุดที่ห้ามแก้ถ้าไม่เข้าใจ) ก่อนแก้ส่วนสำคัญ
- ทดสอบหลังแก้ทุกครั้ง

## 🧠 8. การนำไปใช้เชิงพาณิชย์

### สามารถนำไปต่อยอดได้

- ✅ ใช้เป็นฐานพัฒนาระบบให้ลูกค้า
- ✅ ปรับแต่งเป็น product แล้วขายเป็นบริการ (เช่น "รับทำระบบห้องสมุด")
- ✅ ใช้เป็นฐานทำโปรเจคส่งงาน
- ✅ ใช้ภายในองค์กรขนาดเล็ก
- ❌ ขายซอร์สโค้ดต่อในรูปแบบเดิม
- ❌ แจกจ่ายให้คนอื่น

### ไม่รับประกันผลลัพธ์ทางธุรกิจ

Template นี้เป็น **เครื่องมือ** ไม่ใช่ **โซลูชันสำเร็จรูป**:

- ไม่รับประกันว่าจะเหมาะกับทุกธุรกิจ
- ไม่รับประกันรายได้หรือกำไรจากการนำไปใช้
- ผลลัพธ์ขึ้นอยู่กับการปรับแต่ง การดูแล และ environment ของผู้ใช้

### ผู้ใช้งานเป็นผู้รับผิดชอบ

- **การ deploy** — ผู้ใช้เลือก hosting, ตั้ง server, ตั้ง domain เอง
- **การดูแลระบบ** — backup, update, monitoring เป็นหน้าที่ของผู้ใช้
- **การรักษาความปลอดภัย** — ตั้ง HTTPS, เปลี่ยนรหัสผ่าน, ตรวจ log เป็นหน้าที่ของผู้ใช้
- **ข้อมูลลูกค้า** — ถ้านำไปใช้กับข้อมูลจริง ผู้ใช้ต้องรับผิดชอบการจัดการข้อมูลตามกฎหมาย

## 📌 9. ตัวอย่างสถานการณ์ที่ "ไม่แนะนำให้ใช้"

เพื่อความชัดเจน ต่อไปนี้คือสถานการณ์ที่ **ไม่แนะนำ** ให้ใช้ template นี้โดยตรง:

| สถานการณ์ | เหตุผล |
|---------|--------|
| **ระบบธนาคาร / สถาบันการเงิน** | ต้องการ compliance ระดับสูง (PCI-DSS), audit trail, 2FA, penetration testing |
| **ระบบสุขภาพระดับประเทศ** | ข้อมูลอ่อนไหวสูง ต้อง compliance เฉพาะทาง (HIPAA equivalent) |
| **ระบบ E-commerce ที่รับชำระเงินจริง** | ต้องมี payment gateway, PCI-DSS compliance |
| **ระบบที่มีผู้ใช้หลายพันคนพร้อมกัน** | ต้องมี load balancer, caching, auto-scaling |
| **ระบบที่ต้อง uptime 99.99%** | ต้องมี failover, monitoring, disaster recovery |
| **ระบบหลายสาขา (multi-tenant)** | ต้อง redesign database + isolation |
| **ระบบที่ต้องผ่าน security audit ระดับองค์กร** | ต้อง penetration testing + compliance certification |

> ⚠️ **ไม่ได้หมายความว่าระบบนี้ไม่ดี** — แต่หมายความว่าสถานการณ์เหล่านี้ต้องการระบบที่ออกแบบมาเฉพาะทาง ซึ่งมีราคาและความซับซ้อนสูงกว่า

### ใช้เป็นจุดเริ่มต้นได้ไหม?

**ได้ครับ** — ถ้าเข้าใจว่าต้องพัฒนาต่ออีกมาก:

- ใช้เป็น **แนวทางศึกษา** ว่าระบบจริงทำงานยังไง → ได้
- ใช้เป็น **prototype** ก่อนสร้างระบบจริง → ได้
- ใช้เป็น **ระบบจริงโดยตรง** สำหรับสถานการณ์ข้างต้น → ไม่แนะนำ

## ✅ 10. สรุปขอบเขตการใช้งาน

### เหมาะกับใครมากที่สุด?

| กลุ่ม | ประโยชน์ที่ได้ |
|-------|-------------|
| **นักศึกษา** | ระบบสมบูรณ์พร้อมส่งงาน + เข้าใจโครงสร้างเพื่ออธิบายได้ |
| **ผู้เริ่มต้น Backend** | เห็นสถาปัตยกรรมจริง ไม่มี framework ซ่อน |
| **ผู้สอน** | ตัวอย่างที่ดี มีเอกสารครบ อธิบายง่าย |
| **Freelancer** | template พร้อมต่อยอด เพิ่ม feature ได้ง่าย |
| **ห้องสมุด/ร้านเล็ก** | ระบบยืมคืนครบวงจร ตั้งค่าง่าย |

### ใช้แบบไหนจะได้ประโยชน์สูงสุด?

1. **ติดตั้งและทดลองใช้ก่อน** — กดทุกปุ่ม ทดสอบทุก flow
2. **อ่านเอกสารประกอบ** — README → FLOW → ARCHITECTURE
3. **อ่านโค้ดตาม flow** — เริ่มจาก login → ยืม → คืน → จอง
4. **ลองแก้ไขค่าง่ายๆ** — กฎการยืม-คืนแก้ที่ **หน้าตั้งค่าระบบ** (ไม่ใช่ `.env` แล้ว) → เห็นผลทันที
5. **ลองเพิ่มฟีเจอร์เล็กๆ** — ฝึกทำจริง เรียนรู้โครงสร้าง
6. **ปรับแต่งให้ตรงกับความต้องการ** — ต่อยอดจากฐานที่มี

### ควรมอง template นี้เป็นอะไร?

**มองเป็น "ฐานที่พร้อมใช้และพร้อมต่อยอด"**

- ไม่ใช่ software สำเร็จรูประดับองค์กร
- ไม่ใช่ระบบที่ deploy ได้ทันทีโดยไม่ต้องปรับแต่ง
- แต่เป็น **โค้ดที่ทำงานได้จริง มีโครงสร้างดี มีเอกสารครบ** พร้อมให้คุณเรียนรู้ ใช้งาน และต่อยอดตามความต้องการ

สิ่งที่คุณได้ไม่ใช่แค่ "โค้ดที่ทำงานได้" แต่คือ **"วิธีคิดในการออกแบบระบบ"** ที่ใช้ได้กับทุกภาษาและทุก framework
